## 3. 【重要】ブランチ・コミット運用

GitHub Flowを使い、次の順で作業する。

1. 作業中の変更を確認・整理してから、mainに切り替えて最新をpullする。
2. mainから、作業用ブランチを作る。ブランチ名は下記の「ブランチ名とコミットの種類」参照。
3. 作業ブランチで変更・動作確認を行い、コミット・pushする。
4. mainを取り込み先としてPRを作り、他のメンバーにレビューを依頼する。（[要確認]レビュワー固定する？）*見落とし防止のため、Slack上で連絡すること
5. 作成者以外の1名以上が確認し、"Merge Pull Request"で承認し、mainにマージする。
6. 各自が必要な作業を整理したうえで、mainに切り替えてpullする。

mainに直接コミット・pushしない。PRは原則1つの目的に絞る。
コンフリクト（変更の衝突）は作成者が対応し、分からなければSlack上で班内で相談する。
承認後にコードを変更した場合は、再度レビューを依頼する。

### ブランチ名とコミットの種類

ブランチ名は「種類/作業内容」。作業内容は短い英単語をハイフンでつなぐ。全て小文字で記載する。
**基本的にはfeatとfixを使用すればOK**
例：feat/search-filter、fix/search-error、docs/team-rules。
Issue番号の追加は任意。頻度は今回の班活動での想定であり、使用回数の決まりではない。

コミットメッセージは、講義資料指定の「種類: 何をしたか」に合わせる。

| ブランチ/コミットメッセージの種類 | 使うとき | 例 |
|---|---|---|
| feat / fix | 機能を追加 / 不具合を修正 | feat: 一覧画面に検索を追加 (#3) |
| docs | READMEなどのドキュメント | docs: READMEに班のルールを追記 |
| refactor / chore | コードの整理 / 設定・準備 | chore: 初期構成を追加 |

- 変更内容は日本語でよい。「修正」「更新」だけで終わらせない。
- 関係する変更をまとめ、無関係な変更は別のコミットにする。（1機能1コミット）
- 理由や補足が必要な場合は、空行を挟んで本文に追記する。

## 4. PRの作成とレビュー

タイトルはコミットメッセージと同じ形式にする。
例：feature: 検索に価格フィルターを追加

PR本文は次のテンプレートを使う。
運用時に、リポジトリ直下の.github/pull_request_template.mdへ配置する。

```markdown
## 変更内容と目的（必須）
- 変更したこと：
- 変更した理由：

## 動作確認（必須）
- 確認手順：
- 確認結果：
- スクリーンショット：（画面変更がある場合に添付）

## レビューで見てほしい点
- 特になければ「特になし」

## 未確認・相談事項
- なければ「なし」

## 関連Issue（任意）
なし
```

関連Issueがあれば「Closes #12」などと記載する。
未確認のことは、そのまま未確認と書く。

レビューでは、次を確認する。

- PRの説明と差分が合っている。
- コード変更では、確認者も手元で起動し、変更した機能を試せる。
- 秘密情報や、作業に関係のない変更が含まれていない。

文書だけの変更は、文章・手順・リンクを確認する。
分からない箇所は説明を求め、疑問点を解消してからApproveする。

## 5. 【重要】秘密情報と.envの受け渡し

- APIキー・DBパスワードを、コード・README・PR・Issue・ログに書かない。
- 実際の値を含む.env・.env.localなどは.gitignoreに登録し、コミット対象から外す。（.gitignoreに追加済み）
- コミット前に対象ファイルと差分を確認し、秘密情報が含まれていないか確認する。
- .env.exampleには変数名とダミー値だけを書く。変数を追加したら更新する。
- 秘密情報をAIへの質問に貼り付けたり、AIに対象ファイルを直接読ませたりしない。

.envの共有方法：SlackのDMで共有する
READMEには受け取り方だけを書き、実際の値は載せない。
秘密情報を誤って共有・pushした場合は班および講師に連絡し、該当キー等を無効化・再発行する。

## 6. コーディング規約・Issue

コーディング規約は、次の最小限とする。

- 既存コードの書き方とファイル配置に合わせる。
- 変数・関数には、役割が分かる名前を付ける。
- 作業に関係する範囲を変更する。

既存のチェックツールがあれば、実行方法を共有して利用する。
Issueは任意。不具合や後で対応する作業の記録など、必要なときに使う。
Issueがなくても、作業ブランチ・コミット・PRを作成してよい。

## 7. AIの利用

AIには、実装案・コード作成・説明・修正案・コミット文案・PR本文案を依頼できる。
作業開始時にREADME.mdとAGENTS.mdを読むよう指示する。

人は、差分と動作の確認、Git操作、レビュー、Approve、マージを担当する。
AIのコードも担当者が確認し、理解できない箇所は説明を求めてから取り込む。
詳細はAGENTS.mdを参照する。
